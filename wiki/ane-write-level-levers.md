# ANE 写法杠杆：算子拼写、split-K 与调色板粒度的本机实测

[English companion](en/ane-write-level-levers.md)

同一段数学在 ANE 上可以差一个数量级，而差别不在"用哪个后端"，在**怎么把它写出来**。本页记录
2026-11-10 在 M1 Pro / M4 / M2 上的一轮一手测量：换后端最多 1.2×，换写法最多 9.7×。三个可操作的杠杆
是算子拼写（决定上不上 ANE）、split-K（归约维切分）与调色板表粒度（决定 LUT 快还是慢 3–10×）。

与 [ANE 可达性](ane-reachability.md)、[权重形式](ane-weights.md)、[放置](ane-placement.md) 的关系：
那三页整理 [ANE 论文](https://arxiv.org/abs/2606.22283) 的第三方结论，本页是本机复测与补充，
口径按 [测量](measurement.md)。本页**不覆盖**端到端模型验收、能耗（无 sudo 功耗轨）与 M3/M5。

## 三类变量的量级差

同一块硬件、同一份权重，只换一个变量：

| 变量 | 实测跨度 | 性质 |
|---|---|---|
| 权重格式 / 布局 / 切分 | **最高 9.7×** | 连续，有最优点 |
| 算子拼写（上不上 ANE） | 0% vs 100% 放置 | **二值** |
| 换后端（ANEForge vs Core ML） | ≤ 1.2× | 同图执行基本打平 |

9.7× 来自 M2 上 4096→12288 的 GEMM，`int8b64`（48.0 ms，掉出 ANE）对 `lut4`（4.9 ms）。

## 杠杆一：算子拼写决定放置

**数学等价的三种 MIL 写法，batch-1 时落点不同。** M2 / macOS 27.0.1，4096×4096 GEMV，
`ComputeUnit.ALL`，落点用 `MLComputePlan` 读：

| 写法 | 耗时 | 落点 |
|---|---|---|
| `mb.matmul` | 1.505 ms | **ANE 0/3（全 CPU）** |
| `mb.linear` | 1.462 ms | **ANE 0/3（全 CPU）** |
| `mb.conv`（1×1） | 0.966 ms | ANE 3/3 |

`nn.Linear` 转换出来的正是 `linear`。也就是说**一个标准线性层在 batch-1 时默认不上 ANE**，
Core ML 不报错、结果照样正确，只是在 CPU 上。这是 `[B,C,1,S]` + 1×1 conv 这套布局约定的真正原因：
它不是调优，是入场券。

T≥64 时 `matmul`/`linear` 会回到 ANE（T=64 时 2.55/2.63 TF/s，落点 ANE），**只有 T=1 掉 CPU**。
conv3×3 另有尺寸拐点：M2 上 `[1,64,32,32]` 全 CPU、`[1,128,32,32]` 全 ANE；论文记的 M5 Pro 拐点
在 128→256 之间。拐点随芯片与 OS 变，不要当常数。

拐点以下**放置到 ANE 反而更慢**：C=32 时 Core ML 在 CPU 上 0.090 ms，直连 ANE 要 0.132 ms——
固定 dispatch 吃掉一切。"ANE 利用率高"与"更快"在这个区间是反的。

## 杠杆二：split-K

把归约维 K 切成若干段 conv 再相加。收益随 K 增长，曲线是凸的、有明确最优点：

| 形状 | 芯片 | 最优 k_chunk | 加速 | rmse（不切 → 最优） |
|---|---|---|---|---|
| down_proj K=6144 | M1 Pro | 1536 | **2.46×** | 5.47e-04 → 6.71e-04 |
| down_proj K=6144 | M4 | 768 | **2.83×** | 同上 |
| gate_proj K=2048 | M1 Pro | 512 | 1.13× | 4.98e-04 → 6.35e-04 |
| gate_proj K=2048 | M4 | 512 | 1.34× | 同上 |

三条约束：

1. **K 越大越值钱**：K=6144 给 2.5×，K=2048 只给 1.2×。K 小的层不值得切。
2. **切太细是灾难**：k=256 在三台机器上一律掉到 0.52–0.61×。per-conv 开销吃掉收益。
3. **最优值按芯片×格式变**，没有可移植默认值。M1 Pro 的 fp16 最优 512、int8 最优 1024；M4 的 fp16 最优 512。

**副作用是精度改善，五次复现**：分段缩短了 fp16 累加链。int8 per-channel 的相对 rmse 在
M2 随机权重（8.12e-03→7.37e-03、7.35e-03→6.96e-03）、M1 Pro 两组真实权重
（8.66e-03→7.05e-03、8.85e-03→7.77e-03）上全部下降，最大改善 19%。

**不迁移到 Metal GPU**：同样形状在 MLX 上是 0.72–1.03×（matmul 内核本来就在切 K，手工再切只是加
kernel launch 和中间张量）。这是 ANE 特有的杠杆。

## 杠杆三：调色板表粒度

`constexpr_lut_to_dense` 的码本数量决定它是快还是慢 3–10×，这个参数没有文档，只能被性能暴露。

M1 Pro，真实权重 `[5632, 4096]`，按 128-token tile 归一化：

| tile | int8 ms | lut6（每行一张表）ms | 比值 |
|---|---|---|---|
| 128 | 0.824 | 2.396 | **2.91×** |
| 256 | 0.941 | 6.990 | 7.43× |
| 512 | 0.754 | 6.782 | 8.99× |
| 1024 | 0.690 | 6.702 | 9.72× |

同一位宽、同样落在 ANE 上（`MLComputePlan` 确认全部 NeuralEngine），只因码本数不同：
**每行一张表 5632 张**对 Core ML `palettize_weights` 默认的 `per_grouped_channel, group_size=16`
的 352 张，差 16 倍表数。用后者的 op 级测量是 lut6 3.075 ms（比 int8 的 3.166 还快），
用前者在同一形状上是 2.4–7.0 ms。

论文 §25.2 记了调色板向量尺寸合法集 `{1,2,4,5}`，但没有给逐表数的时延；本页补上这一条：
**码本数量是一个一等性能参数，选错方向就从"比 int8 快"变成"慢 3–10×"**。

字节侧没有意外：实测 `.mlpackage` 权重字节与理论值精确匹配（fp16 1.999×、int8 1.000×、
lut6 0.752×、lut4 0.500× 相对 int8），LUT 表开销可忽略。

## 逐层 program：32 层的切换代价

[放置页](ane-placement.md)留了一个待实测的问题——逐层 Core ML program 在 32 层串行调用时
会不会退化成纯地板成本。本机测量给出的答案是**不是地板成本，但有一个更大的切换代价**：

| 口径 | 实测 |
|---|---|
| 单层 program 单独常驻 | 3.05 ms |
| 32 层全常驻，顺序跑一遍 | 1185.5 ms = **37.0 ms/层** |
| 比值 | **12.1×** |

单层 3.05 ms 远在 0.23 ms 地板之上，所以不是 dispatch 下限问题。12× 的差距出现在
**32 个程序（合计约 3.2 GB 权重）同时常驻**时，与 enginetailor 记录的"驻留权重超过约 2.4 GB
后每次切换都 reload"一致。结论：逐层 program 的代价不在 launch 次数，在**常驻权重总量越过工作集后的
重载**；要降它应减少常驻字节或合并相邻层，而不是加大 tile。

## residency 不一定是约束

同一轮测量里，17.2 GB 的 M1 Pro 在 ANE 常驻权重 3.20 / 4.03 / 4.88 GB 三档下，
测量窗口的 `vm_stat` Swapouts **全部为 0**，没有换页。

这与"高份额被 residency 卡住"的既有结论不矛盾但不可外推：那条结论来自 16 GB 主机。
**换一台 RAM 更大的机器，这堵墙可能根本不存在**——在为绕开它做工程之前，应先用
`vm_stat` 在目标主机上确认它存在。本轮就是先造了绕行方案、后才发现墙不在，代价是一整条白做的实现路径。

## 采用条件

- 全部为 2026-11-10 单轮一手测量，macOS 27.0.1 / coremltools 9.0，芯片为 M2（笔记本）、
  M1 Pro（16 核 ANE）、M4（mac mini）。**未在 M3 / M5 上复核。**
- 时延为中位数；Core ML 侧尽量用 `last_predict_duration_in_nano_seconds`（引擎内时间，剔除 Python 包装），
  直连后端侧只有墙钟，故对 Core ML 偏有利。
- 精度为单矩阵相对 rmse 对 float64 oracle，**不是模型验收**。量化格式的端到端影响另见下。
- 测量在持有本机 Metal 双锁的窗口内进行；一次与软件安装重叠的读数偏高 2.6%，已重测。
- **随机权重会骗人**：split-K 在 M2 随机权重上读出 1.59×，换真实训练权重后降到 1.13×。
  任何写法结论都应在真实权重上复核。
- 本页不含功耗测量（本机无免密 sudo），不含端到端模型验收。
