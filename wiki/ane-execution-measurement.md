# ANE 执行与测量：compile-once、常驻状态与可观测边界

[English companion](en/ane-execution-measurement.md)

ANE 不是逐指令驱动的设备：主机交出一份已编译程序与操作数缓冲，按门铃，然后等完成通知；引擎固件自己走一遍
静态图。这个模型决定了时延预算、状态驻留方式，以及"测什么、测不到什么"。本页取自
[ANE 论文](https://arxiv.org/abs/2606.22283) 的 ch2、ch5、ch6、ch19、ch29–33，数字是论文在 M1/M5 上的
第三方测量，不是本机结果。Core ML 是发布路径；Core ML 以下的直连路径**只用于测量与研究**。

## 一次调用里大部分不是计算

小图（3×3 conv 8→8、relu、mean）在热循环里约 190 µs/次，其中约 98% 是软件+固件：约 25 µs 用户态绑定与
主机 fp16 拷贝、16 µs 构建固件请求、2–3 µs 门铃、**约 130 µs 固件往返**、10 µs 内核侧完成（§2.3，table 2.3）。
驱动同时只允许一条固件命令在飞，两个提交线程串行 1.04×（§2.4）。

由此得到三条工程约束：把编译移出循环；不要指望并发主机调用互相重叠；把"compute 项小于下限"的算子当 dispatch
问题处理（融合、加 batch、换设备），而不是当 kernel 问题处理。走 Core ML 时，一次 `evaluate` 在驱动层
表现为三次 driver→firmware 请求：输入 cast、推理、输出 cast（§33.3 的 signpost 证据）。

## compile once / dispatch many，但每个具体形状各编一次

编译产物按内容寻址缓存在磁盘上，key 覆盖每段的网络结构与权重容器、源 URL、选项与 platform；改动任一权重、
形状、算子集、device mask 或 segmenter 都会重编，新程序的首次 dispatch 还要付一次生成可加载硬件形式的一次性
成本（§2.1、§5.2.1）。所以"同一模型换一个 shape"不是免费的重用，而是新的一段编译+首跑成本。

图是静态的：没有指令流、没有 PC、**没有数据相关分支**；固定 trip count 的循环展开，数据相关长度必须在主机侧
解决或重构成固定形状。符号形状能解析但在直连路径上下不去，实际只有三种做法：pad 到固定最大长度、按长度桶
（bucket）编译若干份、或按长度重编（§2.5、§19.8）。

## 常驻状态是"别名"，不是更快的路径

把一个 buffer object 同时绑给第 N 次调用的输出端口与第 N+1 次调用的输入端口，KV cache 或 optimizer state
就可以留在片上，主机每步只送新的输入（§2.6）。论文明确说明这**不提高引擎吞吐**：逐步 call 与一次绑定
的端到端速率相同，省的是主机 CPU 与拷贝（§6.4）。M1 上原生的 in-place state 引擎被 stub 掉，别名是唯一路线。

## 测量陷阱

| 陷阱 | 含义 | 出处 |
|---|---|---|
| 小图上 98% 是开销 | 图变大后占比下降，但绝对 ~190 µs 不会变 | §2.3 |
| 固件往返不可再细分 | per-task-descriptor latency profiler 被门控，130 µs 是一整块 | §2.3 |
| warm-eval 成本是固件往返-bound | 数 IOConnect 调用次数会高估 dispatch 成本 | §5.2.2 |
| burst 边界 | 约 3 次调用的 warmup（第 1 次约 3.6× 稳态）；亚秒空闲 1.2–1.7×；5 s 空闲后首次约 260 ms | §10.5 |
| rail-off 重臂 | 空闲约 100 ms 后上电成本涨到约 0.5 ms 并进入平台 | §31.3 |
| 没有频率/电压遥测 | 引擎无 DVFS；只有时钟态驻留与 throttle 触发计数可读 | §31.3、§33.3 |
| 共租户 | 有 co-tenant 时约 +202 µs（2.33×），连一个极小竞争者也会加约 +178 µs | §32.2 |

前两行与"rail-off 重臂"是两套不同口径的证据：ch10 的 burst 表测的是**首次调用被拉长**，ch31 的 0.5 ms 是
**电源域重新武装**的固定成本。引用时各自带条件，不要相加（工程推断）。

## 还能观测到什么

未授权进程仍可读：整机级 DRAM 读写字节、能量（mJ）、时钟态驻留、throttle 触发计数、自由运行时间戳，
以及 per-dispatch 的 signpost 流。被门控的是 24 个 per-task-descriptor 计数器：runtime 对第三方客户端把
stats mask 清零，强行置非零会在 load 阶段失败，因为编译产物里没有 stats-descriptor section（§33.3）。

论文自己的 2 MB 工作集证据就是用可读通道拿到的：一次 dispatch 搬 426 MB、强度 60 FLOP/byte、79–90 GB/s、
约 0.48 pJ/FLOP。这是"不依赖被门控计数器"的 ANE 测量模板，值得照抄到本仓库的测量流程里。

## 编译服务风险

编译失败会重启共享编译服务；失败到达速度快于重启间隔时，无关编译也会被拖慢，所以重试至少间隔约 15 s（§19.4）。
M1 上可训练卷积的编译时间随 batch 增长（4 约 1.9 s、64 约 35 s、128 约 79 s、1000 不收敛），宽 reconvergent
fan-in（约 12 个以上分支）单 cluster 约 9 s 见顶（§19.5）。这些是观测值，不是跨版本的契约。

## 边界声明

Core ML 以下的一切——loader、daemon、IOKit selector、程序容器、固件命令协议——都是私有的、不受支持的、
随 OS 更新失效、不满足 App Store 条件的（ch6、ch27–30）。它能用来测量、能解释 Core ML 的行为，但不能作为
发布实现的基础。对外承诺的能力只走 Core ML。

## 采用条件

- 时延与开销数字来自论文的 M1（ch27–33 中的 "M1" 机器实际是 M1 Max 级器件，`h13g`/16 核；base M1 的核数在
  编译目标表里是 4——跨芯片引用时不要混用）。
- 260 ms / 0.5 ms 两个 idle 数字是不同阶段的口径，不能相加；本机采用前应按 [测量页](measurement.md) 重测。
- 论文在直连路径上测得的可观测性（哪些计数器被门控）不构成 Core ML 路径的保证；Core ML 的 analytics 字段
  与 `MLComputePlan` 需要单独核实版本行为。
- 本页不含任何本机测量；所有数字边界见 [roofline 页](ane-roofline-dispatch.md) 与
  [形状/数值页](ane-shape-numerics.md)。
